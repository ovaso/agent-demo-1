# 05 · 最小启动规格与结果接纳

[阅读索引](README.md) · [统一执行规格](04-unified-agent-spec.md) · [领域术语](../../CONTEXT.md)

日期：2026-09-11。状态：设计草案，未实现。本篇细化统一设计中的启动与完成流程；字段名、状态名和工具名均为设计建议，不是当前可调用接口。

用户已明确主、子 Agent 必须统一包含精选上下文、系统提示词、当前任务、任务验证验收条件与 budget。本篇保留这些内容，解释“具备启动配置”和“已经完成调查、取得验证证据”的区别。其余权限变更、完整版本矩阵、材料存储与队列恢复问题继续见第 04 篇。

根据后续确认的[运行事实、Shell 对话与任务流程](06-shell-facts-and-task-flow.md)，本篇只约束已经决定进入任务的 Agent。应用启动默认进行对话，不要求每条会话输入满足本篇的任务启动/完成契约；任务入口采用用户明确的四参数形式，公共 Blackboard 始终存在于任务中，planner 只控制规划能力。

## 1. 最小启动规格的含义

最小启动规格是同一 Agent 执行规格在首次派发前需要达到的完整程度，不增加另一种 Agent 类型或执行器。

这里的“首次派发”指任务 Agent 的首次请求，不是 Shell 的首次对话请求。模型判断为任务或用户选择 `/plan`、`/resolver` 后，才创建并检查这份规格。

启动前应当能够回答：这是谁的任务，要交付什么，遵守哪些规则，从哪些已有材料开始，允许采取什么行动，按什么要求判断交付，最多能使用哪些资源。完整计划、调查结论、全部相关文件和已经通过的验收证据不属于启动必要条件。

统一使用三类记录：

- **创建请求**：用户或协调者提供的任务及可选配置，可以采用宿主已有默认值；没有派发资格。
- **生效规格与初始状态**：宿主和 Runtime 解析、校验并保存后的完整启动依据；依赖及预算满足时才允许派发。
- **运行状态与结果提案**：执行中累积的材料、进度、证据、用量和交付结论，不回写伪造初始条件。

“最小”约束生效规格的完整性，不要求用户手工填写所有字段。主任务与子任务使用同一组字段和校验；根/父标识、模板、Provider、默认限额由应用与 Runtime 装配。

## 2. 必备配置及允许的未知项

| 配置组 | 首次派发前必须有 | 可以留待执行中形成 |
| --- | --- | --- |
| 身份与执行绑定 | Agent/根任务/父任务关系、角色、当前 Provider 和工作区引用、依赖状态 | 后续任务分解和新的委托；不允许缺少当前归属 |
| 当前任务 | 非空原始指令及来源、当前目标、已知范围/约束、预期交付；可标注尚需解释的要求 | 根因、解决方案、具体步骤及新发现；原始要求始终保留 |
| 系统提示词 | 解析完成的公共/角色/适用项目规则文本或可恢复快照引用 | 经授权修订后的新版本；不允许启动时引用尚不存在的模板 |
| 精选上下文 | 选择策略和上限、初始选中集合、来源/版本及选择结果；确无材料时集合可为空且说明原因 | 调查中取得的材料和验证证据；空集合不代表跳过选择 |
| 任务验收 | 至少一条有来源的交付要求，明确已确定的验证方式及待细化的绑定；所有条件初始可处于未验证状态 | 具体检查对象/命令、证据和通过结果；待细化项在完成接纳前必须解决 |
| 能力与工作意图 | 生效工具集合、内部控制能力、允许调查/执行的范围、当前工作意图 | 后续明确获准的调整；模型不能自行填入更高权限 |
| Budget | 已绑定根账本、局部额度、输出限制和现有输入/工具/存储限制，或明确引用根限制；余额来自账本 | 已用量和预留随执行变化；不能用 unknown 表示无限额度 |

空值必须有字段语义：主 Agent 的父标识为空是正常根任务；`selected_context.items=[]` 可以表示没有相关初始材料；`dependencies=[]` 表示无依赖；`tools=[]` 可以用于仅依据现有材料回答。未知 Provider、未解析的预算配置和缺失 system 快照不能以相同方式通过校验。

选择策略与初始材料引用属于启动规格；后续选中集合保存在带修订的运行状态中。普通材料追加不重新生成全部执行规格，也不自动使无关验收结果失效；任务要求或授权变化才进入相应的规格修订流程。

## 3. 三种条件，分别在不同时间检查

| 类别 | 含义 | 示例 | 未满足时 |
| --- | --- | --- | --- |
| 启动前置条件 | 决定是否能够理解并开始获准工作的输入、配置和依赖 | 明确任务对象；可用 Provider；合法权限；对“汇总这份附件”已有可获取附件 | 等待依赖、要求补齐必要输入或报告配置错误，不发送本应被阻止的模型请求 |
| 调查目标 | 任务要查明的事实和方法 | 故障原因、相关文件、哪些日志有价值、怎样验证某个假设 | 记录为待调查，可以开始权限范围内的调查 |
| 完成验收条件 | 宣告完成时必须满足的交付要求 | 结论有证据；指定检查通过；产物符合约束 | 可以继续执行；最终未满足则不能完成 |

某份材料是不是启动前置条件，取决于当前任务动作，而不是它最终是否重要。“取得一份报告”可以在尚无报告时开始；“只依据指定报告作最终判断”需要先有可获取的报告。不能仅因某份材料被标为“必需证据”就一律阻止调查。

候选材料条目可标记用途为启动输入、调查线索或完成证据。启动校验只强制当前真正需要的启动输入；原始约束、权限和未知工具副作用始终由规格/状态保留。调查目标不是绕过副作用核实或缺失授权的理由。

对于调查、实施兼有的任务，可以先做不依赖未决选择的获准工作。只有依赖该选择的动作等待明确，不把所有任务强制改为只规划模式，也不增加每次执行前的例行确认。

## 4. 自然语言任务如何形成初始规格

### 解析与默认来源

创建者必须提供任务指令；结构化范围、验收、材料引用和局部预算可以一同提供。宿主配置提供 Provider、角色模板、工具授权及默认资源限制，Runtime 产生归属标识并绑定有效版本。

自由文本先完整保留为有来源的 task 原始要求，不要求额外调用一个模型才允许创建任务。无法直接提取的细节留在原文并标记待解释，不能由规则拼接器假装已完成语义理解。缺少短目标或交付摘要时，可以暂以原始请求为依据，不强行生成一个可能改变含义的摘要。

明确提供的结构化验收优先保留。只有原文时，初始验收可包含一个“满足来源请求中的交付要求”的来源绑定项，标记 `binding=pending`；该标记允许开始工作，但不具备完成接纳资格。不能默认为 ModelReported，从而降低原文中可能存在的程序验证要求。

### 首轮及后续细化

Agent 在正常预算内读取任务和现有材料，提出有来源映射的任务解释与验收绑定。来源绑定项在初次解释后必须成为非空的具体条件集合，子条件保留对原文及原项的引用；不得通过删除原项遗失要求。最终提交之前没有完成绑定的任务保持未完成。

初次补全允许在原授权范围内明确如何验证，并由 Runtime 检查条件非空、来源关联、工具授权和已知验证方式等结构约束。若原条件已经绑定为程序验证或操作者验证，模型不能把它改为较弱方式；已经明确的范围和条件不能作为“初次解释”被删除。对无法机械判断的自然语言完整性保留解释来源及证据等级，不声称 Runtime 已证明语义等价。

常规细化不要求用户逐项确认；影响任务方向、用户原始要求或授权的实质歧义需要澄清。子 Agent 对自身任务的细化也使用相同规则，但不能修改其承担的根要求或扩展任务范围。根要求需变化时交回协调者按原授权处理。

验收结构中应区分 **绑定状态** 与 **验证状态**：`binding=ready` 表示判定方式和对象已明确；`verification=pending` 表示证据尚未产生。前者是完成接纳的准备条件，后者在启动阶段是正常状态。

## 5. 首次派发的检查

1. **任务有效**：指令非空、有来源；关键任务对象足够明确。调查结论未知不算输入错误。
2. **绑定有效**：角色、系统提示词、Provider、工作区和工具授权解析完成；主/子归属正确。
3. **材料可用**：完成有界选择；真正的启动输入可读或有已保存内容，依赖未就绪则排队。待调查材料不要求已经取得。
4. **验收存在**：有非空、可追溯的交付要求；未确定的验证绑定显式标记，不能伪装成已通过。
5. **边界满足**：完整模型请求、工具批次及续接协议合法；请求和存储不超限，实际派发时满足根/局部预算。
6. **能够恢复**：启动规格、初始材料与状态已成功提交；模型请求预留按既有规则落盘后才发送。

这组检查只判定能否开始。完整计划、所有来源正文、已查明根因、验收通过结果以及是否必然能在当前预算内完成，都不作为首次派发的承诺。

当前步数默认值继续按第 04 篇继承。选择上限等新增配置仍需在实现前定稿；在此之前不能发布接受这些新字段却没有实际限制行为的接口。

## 6. 一个主任务和一个子任务示例

用户请求：“梳理系统提示词的注入流程，比较主 Agent 与子 Agent，给出代码依据，不改文件。”

| 字段 | 主 Agent 的启动内容 | 子 Agent 的启动内容 |
| --- | --- | --- |
| 当前任务 | 回答完整请求，保留只读约束 | 调查子 Agent 提示词初始化，保留父任务只读约束 |
| 系统提示词 | 已解析的公共规则与协调职责快照 | 同版本公共规则与执行职责快照 |
| 精选上下文 | 已知会话要求、相关设计入口及已有实现引用 | 父任务要求映射、相关设计与已发现的子 Agent 实现引用 |
| 未知项 | 完整调用链、主/子差异及所有代码位置 | 初始化经过哪些函数、任务消息如何注入 |
| 验收要求 | 比较两类流程，结论带代码位置，说明未确认事项 | 说明初始化过程并给出可定位证据 |
| 验证状态 | 未验证；可先采用明确的模型报告与来源引用方式 | 未验证；相同证据等级及约束 |
| 能力 | 获准的读取、搜索及协调能力 | 获准的读取、搜索及协作能力 |
| Budget | 根初始 8 步、有限续期硬上限 32，其他限制来自配置 | 同一根账本，局部 4 步，其他限制继承 |

以上是装配完成后的示意，不要求应用在不理解自由文本时自动推导出这张表。如果启动时没有已知实现引用，精选材料可以仅包含已有设计材料；若连相关设计也未知，则记录空材料原因，从获准读取和搜索开始。验收要求已在请求中存在，代码依据可以在调查中形成。

## 7. 统一结果提案与接纳

启动允许未知调查结果，完成需要明确的交付和证据。建议新增一个 Runtime 专用结果提交入口，例如 `runtime_submit_result`；继续走核心控制工具路径，首版可沿用 JSON 字符串承载结构化参数，不要求改造所有 vendor 的工具 schema。该工具目前不存在。

主、子 Agent 都提交相同的结果结构：

| 结果字段 | 内容 |
| --- | --- |
| 任务绑定 | 当前任务、规格/任务修订及执行尝试；由 Runtime 校验归属 |
| 交付状态提案 | 请求接纳完成、报告阻塞或报告失败；不能直接改 Runtime 状态 |
| answer | 面向交付对象的最终说明 |
| criterion_results | 每项验收条件的标识、结论、实际证据和待解决问题 |
| artifacts / evidence | 产物和证据引用，包含所针对的版本及真实工具调用关联 |
| unresolved | 未完成条件、缺失信息及已知限制；没有时为空 |

接纳过程应当有确定顺序：

1. 核对任务、尝试与结果版本，覆盖全部必需验收条件；未完成的验收绑定阻止完成接纳。
2. 核对引用是否可解析、证据是否属于本任务可使用的结果、判定方式和目标版本是否匹配。
3. 按每项已绑定方式判定。ModelReported 保留模型报告等级；程序类验证使用实际工具结果与已声明判定条件；OperatorVerified 只使用操作者明确结果。模型填写“passed”不直接成为程序判定。
4. 缺少必要验证时，返回所缺检查与证据；若需要新执行，则由被授权的执行者在原预算内调度，结果提交工具本身不隐式执行额外业务工具或调用新模型。
5. 成功接纳时与结果、验收状态及任务状态一同提交。未通过时保留提案和原因，在剩余预算内修正；预算不足则暂停，不调用超预算的收尾模型。

验证绑定需指出谁能提供证据：本 Agent 的获准执行、协调者安排的验证或操作者。子 Agent 无权运行所需检查时可以报告阻塞并交回；主 Agent 同样必须由 Runtime 依据已绑定规则接纳，不另行假设总有一个上级模型替它验证。

最终文本与完成状态分开。模型未走结果提交入口的自由文本仍可作为过程输出，不能直接完成采用新规格的任务；已接纳的 answer 才作为正式交付。兼容旧入口的行为需要迁移说明，不在本次修改当前 CLI。

提交以 Runtime 的调用标识和任务/尝试版本记录；已提交调用恢复后重放读取已有接纳结果，不重复结算完成或消耗。新的提交调用若针对已完成任务，按已完成状态拒绝或返回已有结果，不能再执行验证副作用。重试次数、提案正文与保留数量受工具调用、结果和检查点限制约束。

## 8. 如何继续完善完整设计

本篇先补足启动与交付的流程建议。接下来按以下顺序形成可编码规则：

1. **定稿创建与结果接口。** 确定字段、继承与空值语义、初始验收绑定、结果提交、接纳失败响应和对应状态转换。五类必备配置都保留，但不要求已有调查结果。
2. **定稿权限与版本矩阵。** 明确任务、能力、模板、材料、计划及尝试之间的依赖；权限收紧停止新的越权派发，材料更新只影响依赖它的验证。
3. **定稿材料和请求预算。** 明确可恢复正文、引用、提交与清理，以及 system、任务、材料、历史、tools 和协议开销的总量分配。
4. **定稿排队、取消与恢复。** 补齐创建请求幂等、依赖失败、父任务取消和旧格式迁移，再给出完整人工验收场景。

继续维持共享 Provider、顺序调度和平面团队，避免把并行、递归委托和自动上下文策略并入这一轮必要工作。统一数据结构、增加系统提示词模板或补上一张配置表都不能替代上述行为规则。

## 9. 本篇的验收场景

后续实现需要人工核对：调查任务缺少结论仍可启动；没有额外材料时记录选择结果并可开始搜索；真正缺少启动对象时明确等待输入；原文验收尚待解释时可以调查但不能完成；所有条件已绑定且证据不足时仍未完成；子 Agent 使用与主 Agent 相同的结果提案；模型自报通过不能替代程序验证；提交结果后中断恢复不重复结算；预算耗尽时不再调用模型做验收或收尾。

本次只完善文档，未修改代码、配置或依赖，未运行构建、自动化测试或性能测量。本篇细化方案仍待评审；默认限额、完整权限/版本矩阵、材料存储及兼容期限未在这里假设为已定稿。
