## 思路如何演进

1. **从 CH 出发。** 原始调研观察稳定前缀与持续追加的缓存收益，同时指出高命中并不减少窗口占用，也不消除旧信息干扰。
2. **转向上下文生命周期。** 用 Epoch 内稳定追加、边界集中清理来协调缓存与有效性；锯齿是大小变化曲线，Epoch 是生命周期，两者可以并存。
3. **提出可调模式。** 用户提出将 CH 与上下文策略纳入配置。最初讨论过 `cache / balanced / compact` 三档，但这些档位主要改变压缩水位，不能说明上下文精准性的独立收益，因此没有作为最终模式体系保留。
4. **用户提出动态抽调与独立选项。** 用户进一步提出根据当前问题动态抽取有效上下文，即使可能改写或重排请求前缀；据此将构建方式区分为 `append / selective`，并将阈值来源与水位独立配置。
5. **用户补充压缩触发的维度。** 轮次、水位、Token 量应独立于构建策略。后续提案明确轮次可与一种容量条件组合，同时区分触发阈值和压缩后目标。
6. **评估设计完整性。** 当前策略框架已较完整，执行顺序、选择算法、Token 计量、状态恢复和配置契约仍需细化。第 04 篇保留这些问题，供后续整理与研讨，不视为已经确定的实现方案。
