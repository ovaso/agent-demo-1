# 01 · 自适应 Agent 执行设计

[阅读索引](README.md) · 下一篇：[02](02-implementation-progress.md)

文档性质：整体设计；包含已实现与后续目标，具体边界见实现状态。

状态：分阶段实现中。可恢复 Loop、计划与 Blackboard、Graph 路由、平面 Agent 委托及消息协作已提供；已提交功能、验证结果和当前限制见 [当前实现状态](02-implementation-progress.md) 与 [运行时 CLI](03-runtime-cli.md)。本文保留整体目标，包括后续仍需评估的并发能力。

## 目标与现状

在现有 Agent Loop 上增加模型驱动的 Loop / Graph 路由、途中双向切换、计划与重新规划、共享工作板（Blackboard）以及多 Agent 协作。任务在这些操作前后共享恢复进度和执行预算。

当前 `agent-core/src/agent/runner.rs` 按模型轮数限制执行，调用模型后顺序执行工具，并在整批工具完成后保存上下文。`ContextStore` 持久化会话，`MemoryStore` 管理长期记忆，`RunTrace` 已有运行与父子 span 标识。当前模型接口为同步 `&mut self` 调用，工具接口具有 `Send + Sync`；这些条件本身不意味着现有 Agent 可以直接并发共享。

## 四个独立维度

| 维度 | 选择或内容 | 职责 |
| --- | --- | --- |
| 工作意图 | 只规划 / 自动规划并执行 | 决定是否允许进入实际任务执行 |
| 任务计划 | 目标、约束、工作项、依赖、验收条件 | 描述需要完成什么 |
| 执行模式 | Loop / Graph | 决定如何推进剩余工作 |
| 任务分派 | 单 Agent / 多 Agent | 决定由谁承担工作 |

Blackboard 向这些维度提供共享证据与结果。统一运行时负责落实状态转换、预算、检查点与恢复。

Plan 可以通过 Loop 执行，Graph 节点可以运行一个 Agent Loop，Loop 也可以委托子 Agent。切换执行模式不等于改变用户目标，也不自动改变只规划或允许执行的工作意图。

## 规划、路由与执行

### 计划规划

计划至少包含目标、约束、工作项、输入引用、预期产物、依赖、验收条件以及未解决问题。简单任务允许只有一个工作项，不强制为每个输入创建复杂图或额外进行一次独立规划调用。

Planner、Router 和 Coordinator 是逻辑职责。首版由同一个主 Agent 承担，通过一次模型响应同时提交计划提案、路由决策与任务委托；运行时验证这些结构化结果后执行。确定性的节点调度和预算判断不再调用模型。

模型提出计划，运行时校验标识唯一性、依赖有效性、可用执行能力、计划规模与必需验收要求。首版 Graph 使用有向无环任务依赖，修复通过有界节点重试或新的计划版本表达；不要让模型生成无界控制流或任意可执行脚本充当调度器。

### 显式 Plan Mode

用户选择只规划时，允许必要调查、读取以及内部计划和 Blackboard 持久化；禁止执行实际任务的写入、发布等动作。只规划的限制对子 Agent 同样生效，不能通过委托或切换 Graph 绕过。

该限制通过可调用能力集合执行。现有通用 `run_cmd` 不能仅凭提示词就成为只读工具；若没有可验证的限制，计划模式中不提供它，改用明确的读取和搜索能力。内部保存计划与执行元数据不属于修改用户工作产物。

只规划交付可恢复的计划，随后进入等待执行指令的状态。自动执行工作意图则可在已有授权范围内完成规划后继续，不因每次规划或重新规划增加确认环节。只有缺失必要信息或超出已有任务范围时才需要用户介入。

### 入口与途中路由

入口根据任务规模、依赖、探索程度和可用预算选择 Loop 或 Graph。途中在阶段完成、阻塞、新依赖出现或明确的修复需求时重新评估；保持当前模式是合法决策。

支持两种范围：节点内临时委托 Loop，完成后返回父 Graph；整体将剩余工作切换到另一模式。切换提案必须携带目标范围、剩余工作、已有结果引用和未满足的验收条件。

模式切换在安全边界发生：首版等待已启动的工具批次完成并结算、相关子任务到达可暂停边界后再提交。执行结果未知的外部操作必须先进入待核实状态，不能以切换模式跳过。任务边界失效时先取消或暂停相关工作，保留其历史与副作用记录。

### 计划版本

计划定义与工作项执行状态分开存储。计划定义在同一版本内不可原地修改；执行进度可以持续更新。重新规划生成新版本，并记录新旧工作项的延续、替代、取消和结果复用关系。

每次任务委托绑定 `plan_version`、`work_item_id`、`attempt_id` 及输入版本。启用新版本时使旧委托失效或显式迁移。旧 Agent 的迟到结果仍可作为候选证据保留，但不得自动完成新计划工作项；运行时校验当前委托与版本，协调者需要复用时提交显式决定。协作请求和等待关系同时检查有效性：关联工作被替代或取消时，将请求标为失效或显式迁移，并唤醒等待者处理，不让旧请求永久挂起。

已完成结果仅在相关输入与验收条件仍有效时复用。重新规划不能抹除已发生的工具调用，也不能静默移除用户要求的验收条件。

## Blackboard 与执行状态

### 数据归属

| 数据 | 所属职责 |
| --- | --- |
| 单 Agent 的消息与工具对话 | Context |
| 跨任务的长期知识和偏好 | Memory |
| 本任务的证据、假设、决定、阻塞和产物引用 | Blackboard |
| 计划定义与版本关系 | Plan |
| 运行位置、工作项状态、委托、预算、待执行调用 | RunState |
| 耗时、用量与事件展示 | Trace |

Blackboard 可以展示计划与执行进度的投影，但不再维护第二份可独立修改的任务状态。原始工具结果、日志和大文件保持独立引用；不要将所有 Agent 的完整上下文复制进共享工作板或每次模型请求。

建议记录字段：`entry_id`、`run_id`、`kind`、作者 Agent、工作项与计划版本、输入版本、来源引用、内容或产物引用、条目修订号和有效状态。分类至少区分观察、假设、决定、阻塞、产物与验证结果；模型陈述不会因为写入工作板就成为已验证事实。

### 写入与读取规则

Agent 读取与当前工作有关的有界快照，返回结果和更新提案。运行时是共享状态的唯一提交者，依据条目或工作项的预期版本检查冲突。互不冲突的条目允许追加；同一结论的冲突保留来源并交给协调者处理，不采用最后写入者静默覆盖。

Agent 不直接更改其他 Agent 的完成状态、总预算或计划生效指针。决定计划生效、接纳任务结果与扣减预算均由运行时提交。新证据触发后续规划评估时记录消费位置，避免每次轮询相同条目都触发重新规划。

限制每次读取条目数与字节数、单条内容大小以及任务累计存储量。超限返回明确的分段读取或归档要求；需要恢复的调用记录和验收证据不得静默裁剪。引用必须能解析到持久化内容及其版本，不能仅指向可能被覆盖的临时文件。

## 多 Agent 执行

### 委托协议

协调者根据独立工作范围委托 Agent，首版避免为每个角色固定创建一个常驻进程。委托内容至少包含：目标、范围、输入引用及版本、预期产物、验收条件、允许能力、局部预算和所属计划工作项。

子 Agent 持有独立的上下文及可恢复执行状态，返回完成或阻塞状态、产物引用、证据和遗留事项。文本中的“完成”属于提案；运行时依据验收规则提交最终状态。无确定性验收手段时，应显式记录采用模型评估或用户验收，而不将其标作程序验证通过。

规划角色与子 Agent 的模型、工具集合可以不同。应用层负责创建和复用 Provider 实例及其 HTTP Client，核心层不读取环境变量，也不在每轮重新创建网络客户端。

### 上下文选择

默认传递任务相关的精选上下文与 Blackboard 引用，减少重复调查和无关历史。后续可增加显式快照派生策略，用于接续已有调查；必须标注派生版本、限制大小并保持工具请求与结果配对。独立审查使用任务要求、产物及证据，避免默认继承执行 Agent 的自我评价。

无论输入来自精选信息还是快照派生，子 Agent 的后续对话都独立保存，最终按结果协议汇入共享工作板。

### 调度与资源冲突

先实现顺序多 Agent 委托并验证生命周期，再增加可配置上限的并发执行。并发需要独立或受控复用的模型执行实例；不能将整个可变 Agent 包进一个锁后宣称获得并行能力。

共享工作板的一致性不等于工作目录的一致性。写入同一文件或资源的工作必须串行或隔离到独立工作区，再经过显式合并；通用命令无法声明可靠写入范围时按独占写任务处理。验证结果绑定被测产物版本，产物变更后旧结果不能证明新版本通过。

运行时拥有委托队列、活动任务和结果收件箱。父任务等待子任务时不占用可执行工作槽，嵌套委托受深度与总数量限制，避免工作槽被等待中的父任务耗尽。取消和暂停向子任务传播；同步调用的及时中断依赖 Provider 超时及具体工具的取消能力，未具备时只承诺安全边界暂停。发出暂停或取消请求不等于已经停止执行，需在活动调用结算或进入待核实状态后提交相应状态。

## 子 Agent 之间的协作

### 协作通路与决策范围

既支持主 Agent 向子 Agent 分派任务，也支持子 Agent 在已有委托范围内直接交流。直接交流由 Runtime 验证、存储并转发，不要求协调模型逐条转述，也不绕过统一预算和恢复。

| 通路 | 用途 | 提交与生效规则 |
| --- | --- | --- |
| Blackboard | 发布和查阅共享证据、产物及其修订 | 运行时校验条目版本，读取者按来源和版本判断适用性 |
| 协作消息 | 定向提问、答复、请求审查、通知结果更新 | 持久化收件箱投递，答复关联原请求；通知不自动完成工作项 |
| 任务依赖与结果接纳 | 决定何时可继续工作、哪些产物通过验收 | 运行时按当前计划、输入版本与验收规则推进 |

Agent 可发现同一根任务内允许联系的工作项、受托 Agent、职责及可用状态，按工作范围寻找协作者。首版不开放跨根任务通信或隐式全员广播。任务委托指定允许联系和读取的范围，接收方继续受自己的任务范围与能力集合限制。

Peer 请求可用于澄清已有接口、分享证据和交换反馈。要求对方新增工作、扩大范围、调整资源或改变计划时，提交协调者形成新的委托或计划版本；消息内容本身不授予权限，也不能重排对方任务。已有任务的审查职责可以通过消息协作，新增独立审查工作应正式委托并记账。

### 消息与请求生命周期

消息信封至少包含 `message_id`、`root_run_id`、发送方委托与尝试标识、接收方工作项及绑定的有效委托、`kind`、`request_id` / `reply_to`、适用计划和输入版本、内容或 Blackboard 引用以及到期时间。消息来源由 Runtime 填写并验证，重投沿用原 `message_id`。消息正文大小、引用数量、每 Agent 待处理数量和任务累计消息数均有上限。

首版提供请求、答复、拒绝、阻塞和更新通知等明确类型；请求到期时间必须可持久化且有上限。投递记录区分排队、已提供给接收者、已处理；请求记录另有等待答复、已解决、被拒绝、超时、取消或因计划变化失效等状态。发送成功、接收成功与请求解决不能互相替代。

活动接收者在模型或工具的安全边界读取消息，不在半条模型流中插入上下文。暂停中的接收者只累积有界消息，收到消息不撤销用户暂停意图；恢复时检查已过期请求。已完成或取消的受托 Agent 不因收到消息自动重启，Runtime 返回接收者不可用，发送者可读已有结果或请求协调者安排后续委托。

首版请求期限采用持久化的绝对截止时间，暂停期间继续计时；到期事件不触发暂停任务中的新模型调用，恢复后先呈现超时状态。排队或等待超限返回明确错误或阻塞原因，不能静默丢弃控制消息。定向通知默认不要求答复；订阅 Blackboard 更新必须有明确范围、生命周期和消费位置，只能合并不要求逐条处理的通知。

### 等待、唤醒与死锁处理

Agent 可以发布请求后继续独立工作，也可以声明等待特定请求答复、指定版本的产物或前置任务终态。只有实际阻塞推进的等待才添加等待依赖，发送非阻塞请求不自动产生等待边。等待条件明确指定全部满足或任一满足，记录目标标识与版本、截止时间以及失败后的处理策略。普通聊天消息不能改变已注册的等待条件。

进入等待时保存执行检查点并释放调度槽。相关答复提交、依赖完成、超时、拒绝、取消或计划失效事件都能唤醒等待者，由其按剩余预算继续或向协调者报告阻塞。即便并发上限为一，也必须能先保存 A 的等待状态，再执行 B，最后恢复 A。

Runtime 在新增等待关系时检查包含 Graph 依赖、父子委托等待以及 Agent 间请求等待的整体等待图。例如 A 等待 B，而 B 的工作又依赖 A 完成时，应拒绝新增循环等待并返回依赖路径，交由协调者拆分工作或重新规划。没有可执行工作但仍有未完成任务时，检查是否存在有效的外部输入等待或定时器；否则进入明确阻塞状态，不能空转或宣告成功。

协调命令由 Runtime 分派，可向模型提供受限工具形式的接口；等待必须返回可持久化的暂停结果。不要在普通 `Tool::invoke` 内持有运行时锁或执行槽，阻塞等待同一运行时调度的其他 Agent。

如果协作命令以模型工具调用表达，暂停状态须保存原 `tool_call_id` 和同批尚未完成的调用。收到答复或超时后生成该调用对应的工具结果，再按顺序结算其余调用；工具协议完整前不发起该 Agent 的下一次模型请求。模式切换同样不能丢弃这批待返回结果，其他 Agent 则可由 Runtime 正常调度。

### 交付、去重与恢复

协作采用允许重投的持久化投递，由接收者按 `message_id` 去重。将发送者检查点、待发消息与接收者收件箱提交到同一运行存储事务；处理结果、消费位置、关联答复与新的检查点也通过原子提交保持一致。恢复时不能因已标记“提供给模型”就丢掉尚未处理完的请求，也不能因重投再次生成同一委托或重复接纳同一结果。

Runtime 的原子提交与去重只保证内部记录一致。模型响应丢失时可能需要新的模型尝试，外部工具的副作用仍遵循幂等和待核实策略，消息去重不能承诺任意外部操作恰好一次。请求、答复及结果接纳均检查委托代次与输入版本，迟到的旧版本答复保留为证据，不能无条件唤醒新版本等待条件并使其满足。

每次唤醒后的模型请求计入根预算与接收 Agent 的局部额度，消息发送数和协作轮数另外有界；不得因消息重复投递重复记账，也不得通过问答往返绕过模型步数上限。需要新增帮助任务时正式委托，避免以答复请求名义创建无预算的子任务。

### 冲突与联合交付

不同 Agent 对同一问题给出冲突结论时，保留各自证据及输入版本，由协调者选择确定性检查、已委托审查或有界重新调查。不能把多数意见自动视为事实，也不无限要求 Agent 互相说服；达到协作或模型预算后带着分歧进入阻塞或失败状态。

共享接口、补丁和测试结果均关联产物版本。接口更新通过 Blackboard 发布并通知依赖者；执行者不能用旧接口版本的验证结果完成新接口的验收。联合修改继续遵守文件写入隔离和显式合并规则，协作消息不绕过工作区互斥。

例：A 负责接口，B 负责测试。B 通过消息请求字段结构，A 发布带版本的接口说明并答复引用；B 被唤醒后根据该版本测试并提交结果。若期间计划改为新接口，旧答复或测试结果不直接完成新任务；若进程在答复提交后、B 处理前退出，Resume 从 B 的收件箱继续，不再次委托 B。

## 状态收敛与完成条件

工作项区分待依赖、可执行、运行中、等待协作、成功、失败、跳过和取消；每次尝试单独留存，重试不会改写旧结果。Graph 汇合点明确等待全部必需前置项或显式条件分支；被跳过或失败的节点不默认为成功，模型不能以跳过状态移除用户要求。

可选工作失败可以保留说明后继续，必需依赖失败则阻塞后续工作，直到有限重试、重新规划或明确终止。顺序调度使用稳定的工作项顺序；并发结果按标识与输入版本接纳，不依赖返回先后决定计划语义。

根任务完成要求当前计划的必需工作及验收条件已满足、采用的产物版本有效、相关子任务和外部副作用已结算。仍有影响正确性的未答请求、未知工具结果或未处理冲突时不得成功结束；不再需要的请求、订阅和子任务必须显式终止并完成结算。预算耗尽保存为带原因的暂停或失败，不伪装成任务完成。

暂停保留继续执行能力，取消终止当前执行意图；普通 Resume 不复活取消或已成功结束的任务，追加工作通过明确的后续任务处理。需要核实的副作用以独立原因阻塞调度，不能用普通重试清除。

## 共享预算与恢复

### 预算记账

保留最大执行步数，并明确新运行时的口径为模型请求尝试数：规划、路由、执行、模型验收和重试均计入同一根任务预算。另设工具调用数、调度转换数、节点尝试数、重规划次数、切换次数、委托数量及并发上限，覆盖不调用模型的循环和任务扩张。

调用前由运行时持久化预占额度。并发子任务共用根任务账本，同时受到自己的局部上限限制；局部额度不是独立新增额度。未派发的预占可以取消释放，已派发但结果未知的请求不能自动退款后重试。达到预算时停止派发，结算已启动工作并保存恢复状态。

恢复、计划版本变更、模式切换和子 Agent 创建不重置已用预算或续期记录。新任务可采用“初始获准额度 + 总硬上限 + 有限续期”策略：当前额度用完时，根据近期已接纳的新进展，在单次增量和次数限制内续期；状态轮询、失败和重复结果不能用于反复获取额度。达到硬上限或不满足条件时仍保存检查点并暂停。预算判断不额外调用模型，续期先持久化再允许下一次请求，具体规则见 [有界预算续期](../budget/README.md)。

用户显式调整固定总额度不重置用量或续期历史，不能把 Resume 解释为获得一份新预算。旧检查点缺少续期策略时保持固定额度，需明确启用新策略；规划、路由和子任务继续共享根账本。

### 检查点边界

统一持久化根任务与子任务状态、计划生效版本、Blackboard 更新、任务委托及结果、协作消息与消费位置、等待条件及截止时间、预算预占与结算、待执行调用和对应上下文版本。SQLite 后端通过同一提交事务保证这些记录一致；不能用分别调用 `ContextStore.save` 和多个新 Store 的方式假装原子提交。

概念上的提交接口由运行存储承担，可按职责拆表与内存结构，但共享一个事务边界和复用连接。上下文存储兼容适配应从已提交的版本读取或派生展示，恢复以运行存储中的一致版本为准。采用增量更新，避免每条 Blackboard 变动都序列化整个任务树。

模型响应中的工具调用先持久化，然后执行工具并逐个记录结果。外部工具副作用和本地事务一般不能原子提交，因此依旧需要工具幂等键、结果核实或待处理状态；不承诺任意命令恰好执行一次。会话结束工具等终结操作也必须经过统一结算，不能直接删除仍在恢复链上的状态。

Resume 读取同一个根任务，恢复其模式、计划和必要的子任务，不重放用户输入。优先消费已经提交的子任务结果；恢复等待中的父任务时不能重新创建重复委托。旧进程或旧尝试返回的结果通过委托版本验证去重；模型响应丢失后的重试是新尝试，不宣称重现相同输出。

运行记录携带检查点格式版本、执行能力与配置版本以及产物版本引用。恢复前验证兼容性，工具被移除、能力限制变化或输入失效时明确阻塞或迁移，不能静默替换为当前默认配置；敏感凭据继续由应用装配，不写入工作板或消息正文。

同一根任务只允许一个有效 Runtime 拥有者，恢复通过排他所有权和递增运行代次防止两个进程同时调度。任务尝试、消息和提交均校验当前代次，过期执行者不能继续提交或派发新动作。已派发的外部动作不能靠所有权记录撤回，接管前仍需核实遗留副作用。

## 模块落点与兼容性

| 建议位置 | 职责 |
| --- | --- |
| `agent-core/src/agent/runtime/` | 运行状态、统一推进、预算、恢复与存储事务 |
| `agent-core/src/agent/planning/` | 计划与修订提案、结构验证、版本关系 |
| `agent-core/src/agent/routing.rs` | 路由决策和切换校验 |
| `agent-core/src/agent/loop_executor.rs` | 由现有 runner 提取的逐步 Loop |
| `agent-core/src/agent/graph/` | 依赖图与可执行工作项选择 |
| `agent-core/src/agent/blackboard/` | 条目结构、查询与更新冲突校验 |
| `agent-core/src/agent/delegation/` | 子 Agent 委托、生命周期与结果接纳 |
| `agent-core/src/agent/collaboration/` | 子 Agent 请求与答复、收件箱、等待条件与唤醒；持久化复用运行存储事务 |
| `agent-app/src/` 下对应职责模块 | CLI、角色装配、Provider 创建、具体检查与工作区隔离 |

这些是随实现阶段按需建立的模块，不提前生成空框架或新增 crate。复用现有模型、工具与追踪能力，保持 SQLite 可选；工具属性宏不承担调度或共享状态实现。运行存储的 SQLite 实现遵循现有 feature 配置，内存实现可用于无默认 feature 的测试。

现有 `run` / `run_stream` 可作为默认 Loop 的兼容入口。新任务接口区分启动与恢复，并携带工作意图、路由策略和预算。CLI 可逐步提供 `/plan`、`/execute`、`/resume`、`/status` 等入口，实际命令名在实现时确定。

文本流保持增量输出。多 Agent 事件携带根任务、Agent、委托、计划版本与工作项标识，由应用层区分主回答和后台进度，不将多个 Agent 的 token 混成同一段用户回答。展示中计划完成、节点完成、根任务完成和会话结束各有明确语义。

## 交付顺序

1. 统一运行状态、预算与检查点，将现有 Loop 迁入可恢复的逐步执行；保持原有工具顺序和流式行为。
2. 计划数据、Planner 与只规划入口，加入 Blackboard 和计划版本；实现必要的只读调查能力及实际能力限制。
3. 模型路由与顺序 Graph，支持节点内 Loop、重新规划和途中双向切换。
4. 顺序多 Agent 委托与子任务恢复、独立上下文、结果接纳和根预算记账；同时交付子 Agent 请求与答复、Blackboard 更新通知、协作等待与唤醒。
5. 基于测量加入有界并发、冲突资源隔离以及可选的上下文快照派生。

最终范围包含以上全部能力，分阶段用于控制改动和验证成本。Planner、Blackboard、消息与等待状态的接口从第一阶段的数据设计考虑，避免先形成只能恢复单 Loop 的持久化格式。子 Agent 之间的协作属于第四阶段的必要能力，不能仅用并行派发后汇总结果替代。

## 验证与成本

使用脚本化模型、可计数工具、临时 SQLite 和可控中断进行针对性验证：

- 只规划时模型请求写工具、执行模式切换或子 Agent 写入均不能越过工作意图；计划本身仍可持久化和恢复。
- Loop 转 Graph 后恢复保留既有结果、剩余工作、验收条件与已消耗额度；Graph 转 Loop 后同样成立。
- 子 Agent 结果已提交但父任务尚未消费时退出，恢复后不重复委托、不重复结算。
- 新计划生效后旧 Agent 返回，结果保留为候选证据，不错误完成新工作项。
- 同一 Blackboard 条目冲突更新不静默覆盖；不相关条目追加不产生无意义的全局冲突。
- 根预算仅剩一个调用额度时，多个子任务不能同时抢到该额度；切换和重新规划不能绕过耗尽状态。
- 写入完成后落盘失败进入明确的未知状态；恢复不能盲目重跑非幂等工具。
- 产物版本变化后旧测试结果失效，节点完成不能绕过实际验收要求。
- 暂停、取消、子任务失败和计划修改不会遗留无限等待；循环修复受明确上限约束。
- 历史裁剪和上下文派生保留工具调用协议，主 Agent 文本依旧及时流式输出。
- 并发上限为一时，A 等待 B 的答复后释放执行槽，B 可以运行并唤醒 A；不发生嵌套调用阻塞。
- A 等 B、B 等 A，以及消息等待与 Graph 依赖形成的混合环被识别；无可运行任务时能给出阻塞原因。
- 答复已提交但等待者未处理时中断，恢复后继续处理；重复投递不重复接纳结果或创建任务。
- 同一模型响应中包含等待工具与其他工具时，暂停和恢复不遗漏或重复工具结果，未闭合协议前不会发起下一次模型请求。
- 请求超时、对方拒绝或取消、工作项被新计划替代时，等待者获得明确终态；向完成的 Agent 发消息不会自动重启它。
- 暂停期间收到消息不自动恢复模型执行；恢复时绝对截止时间已到期的请求先按超时处理。
- 收件箱、消息正文和协作轮数到上限时明确返回受限状态；Agent 相互发送请求不能绕过根模型预算。
- 新旧接口版本的消息、产物与审查结果不会混用；必需任务失败、未知副作用或冲突未决时根任务不能误报完成。
- 两个进程尝试恢复同一任务时仅一个能派发工作，过期拥有者不能提交；不兼容检查点或缺失工具能明确报错。

Rust 修改后执行项目要求的 fmt、clippy、workspace tests；涉及可选能力和依赖时额外执行无默认 feature 的核心测试。性能使用相同固定任务比较模型调用数、运行时耗时、峰值内存与 SQLite 写入次数。涉及依赖或大量泛型实例化时按项目要求建立 release 可执行文件体积基线并比较，不能以增加 Agent 数量推断速度收益。

本设计阶段仅修改文档，未修改运行代码、引入依赖或执行性能测量。
