# 指标暴露与性能观测

[通用开发](README.md) · [文档总索引](../README.md)

日期：2026-09-11。状态：通用准则已确认，依据为用户明确提出的主动指标暴露与规范化性能观测要求。具体监控产品、SDK、采样方式和接入部署尚未选定；SkyWalking 是候选参考，不代表本项目已接入。

## 1. 主动提供观测入口

有运行状态、资源占用或执行统计的组件，应主动提供只读的指标采集接口。即使当前没有监控消费者，也应在设计和修改相关组件时保留可直接采集内部指标的入口，便于以后接入监控和可观测性技术栈。

简单指标按职责使用 `XxxRuntimeMetric`、`XxxMemoryMetric` 等明确类型；复杂组件的整体可观测状态优先通过 `snapshot()` 返回 `XxxSnapshot`。不要求将每个标量包装成独立类型，也不为没有状态的纯函数制造空指标对象。

“暴露”指库或应用采集方可达的接口，不等于模型工具、业务工具集、HTTP 端点或远程管理能力。指标读取不能改变任务、刷新系统事实、执行工具、清空计数或触发模型请求。

这条准则允许提前提供轻量观测契约，不因“目前没有调用者”而删除它；不因此提前引入监控框架、后台线程、导出服务或一套空的通用指标注册中心。

## 2. Metric 与 snapshot 的职责

| 形式 | 适合内容 | 命名示意 |
| --- | --- | --- |
| RuntimeMetric | 请求/操作次数、成功失败数、队列长度、已维护的累计耗时等 | `AgentRuntimeMetric`、`StoreRuntimeMetric` |
| MemoryMetric | 已持有条目数、缓存容量、逻辑字节数及可说明来源的内存估算 | `ContextMemoryMetric`、`CacheMemoryMetric` |
| snapshot() | 组件状态、相关 Metric、容量、版本、时间及受限/失败摘要的整体视图 | `BlackboardSnapshot`、`RuntimeFactsSnapshot` |

`RuntimeMetric` 描述组件运行统计，不表示指标只能由名为 Runtime 的模块提供。`MemoryMetric` 描述资源占用时，不能与“长期记忆内容”混为一谈；前缀应明确观测对象。

接口形态可以采用以下命名，具体字段随所属组件设计，不是本次新增的可调用 API：

```text
runtime_metric(&self) -> XxxRuntimeMetric
memory_metric(&self)  -> XxxMemoryMetric
snapshot(&self)       -> XxxSnapshot
```

小型 Metric 优先返回轻量值；Snapshot 返回专用只读视图或有界拥有值，不把内部可变对象直接交给采集方。稳定的跨 crate 观测契约可以公开，其他实现保持原模块可见性。

整体状态指足够理解组件健康、进度与资源使用的观测视图，不要求深拷贝全部业务历史或序列化整个组件。Snapshot 可组合已有 Metric，避免维护第二份可独立变化的计数。

已有 `snapshot` 名称若承担其他明确用途，不直接改变其语义。例如当前 [`Context::snapshot`](../../agent-core/src/context/mod.rs)是模型消息副本，不是监控视图。后续扩展应保留兼容性，使用明确区分的观测入口；不能因名称相同就直接把完整消息导出到监控。

## 3. 指标契约与读取成本

每个字段至少说明：含义、单位、来源、统计范围、更新时机，以及重启/恢复或重置后的语义。未知值与零分开；不可采集或仅估算时明确标记，不填看似精确的零或字节数。

需要区分：

- 累计计数、当前值和区间统计；读取累计计数不清零，导出时不能每次把同一累计值再次递增进监控计数器。
- 进程生命周期统计与持久化任务用量；进程重启可能重置前者，不能重置后者，也不能跨任务重复累计同一用量。
- 逻辑内容字节、容器容量、估算堆占用与进程实际内存；说明是否包含共享对象和分配开销，不把 JSON 长度称为实际 RSS。
- 累计耗时与分布；没有足够样本或直方图时不构造 p95/p99 等看似精确的延迟指标。

Metric 读取优先使用组件已经维护的计数和容量；需要新计数时在原状态变化位置更新。不得为每次采集扫描全部任务/历史/目录、重新序列化完整对象，或在热路径添加大量计时、分配和锁操作。

Snapshot 需要说明一致性：在明确状态版本上取得一致视图，或标注为近似采样及其时间范围；不能把跨时刻读取的字段组合宣称为原子状态。并发读取只持有必要的短锁或使用适合当前模型的只读快照，不为观测无条件引入全局锁。

数量可能增长的明细提供上限、摘要或显式分页，并标明受限情况。导出周期、采样频率和格式转换由采集/适配层控制；热路径不负责网络发送或为每个采样点刷盘。

指标维度保持可控。任务 ID、任意路径、用户输入等不默认成为持续增长的指标标签；需要逐任务诊断时使用受限快照、事件或追踪关联。原始环境变量、密钥、完整提示词、模型续接块和业务正文不因提供 snapshot 而自动进入观测数据。

## 4. 性能观测优先采用成熟方案

性能定位和持续监控应优先评估成熟的监控 Agent、采样 profiler、已有插桩库及规范化 API/数据链路。避免把零散手写计时宏、各模块自定的埋点格式和私有导出协议作为常规性能观测方案。

本条针对性能观测方式，不改变项目用于业务工具定义与注册的属性宏职责。

这里的监控 Agent 是观测进程/库，与执行任务的模型 Agent 不同。它可以提供系统、进程、调用链或采样层面的信息；项目特有的队列状态、预算、验收进度和上下文容量仍需要组件提供语义明确的 Metric、Snapshot 或必要事件。

自动插桩与显式业务观测可以共同使用。规范来自 API、字段语义和接入方式，而非是否出现宏：成熟库提供的规范化宏可以使用；必要的业务 span/事件也不因“手动”而被禁止。OpenTelemetry 的官方说明将基于代码的 API/SDK 与零代码方案作为可组合的两类插桩方式。[官方说明](https://opentelemetry.io/docs/concepts/instrumentation/)

| 观测需求 | 优先考虑的方式 |
| --- | --- |
| 组件内部计数与状态 | 直接读取 Metric / Snapshot，再映射到所选观测生态 |
| 调用链与请求关联 | 成熟 SDK、已有库插桩和明确的业务边界事件 |
| CPU、等待及热点分析 | 目标平台可用的采样 profiler 或监控 Agent |
| 平台汇聚和导出 | 应用装配的适配器/Exporter 或外部采集组件 |

性能采样不能自动证明任务是否满足业务验收；Metric / Snapshot 也不能替代调用栈和系统层性能采样。两类入口互补，不合并成一个承担所有职责的监控对象。

## 5. SkyWalking 等候选方案的实际边界

以下为 2026-09-11 核对的外部能力，仅用于后续选型参考，接入时需再次核对目标版本、平台及依赖：

- SkyWalking Rust 提供 tracing、metrics 等观测 API；官方示例需要创建追踪上下文/span、注册指标和启动 reporter。因此不能从“Rust Agent”这个名称推断它会自动识别本项目的所有内部业务状态。[官方 Rust 项目](https://github.com/apache/skywalking-rust)
- SkyWalking Rover 通过 eBPF 提供进程外性能采样，其部署有 Linux 内核和版本/运行环境要求，不能假定可直接部署到当前 macOS CLI 开发环境。应区分开发机工具和未来 Linux 部署方案。[Rover 部署要求](https://skywalking.apache.org/docs/skywalking-rover/latest/en/setup/overview/)
- OpenTelemetry 也提供 Rust API/SDK 方向，但具体组件成熟度和兼容性需按接入版本检查；本准则不选定它或强制所有核心类型依赖其 SDK。[Rust 文档](https://opentelemetry.io/docs/languages/rust/)

采用外部方案前说明：采集目标及覆盖盲区、插桩/采样方式、平台与权限要求、线程或运行时需求、采样/队列边界、停机刷新方式，以及对发布体积和本地运行的影响。需要符号或栈展开信息时单独评估构建配置，不直接修改现有 release 基线来假设已解决性能定位。

## 6. 依赖、接入与故障边界

组件负责定义和更新自身观测数据，采集适配层负责读取、单位/标签映射和导出，应用负责选择后端、采样策略和配置。核心数据类型不绑定某个监控平台，不为提供只读指标就反向依赖应用或 vendor。

本项目后续接入优先复用现有 [`TraceSink` 与追踪边界](../../agent-core/src/trace/mod.rs)、[预算读取](../../agent-core/src/agent/runtime/budget/mod.rs)及状态信息；不因引入标准化出口而丢失当前业务语义，也不在本次删除现有 JSONL 追踪。现有 tracing 行为见[领域说明](../tracing/README.md)。

观测契约可先提供，具体 Agent/SDK/Exporter 随明确接入需求选择。新依赖按实际所需 features 配置，能隔离的监控后端应可排除，不为了一个 exporter 隐式要求所有核心使用者引入异步运行时。

新增外部导出应与任务正确性隔离：网络失败、采样关闭或队列满不能悄悄改写任务状态，也不能无界缓存。记录受限、丢弃和导出错误的观测状态，不能让错误上报产生无限递归。当前本地 TraceSink 的错误传播语义如需调整，应单独设计和验证，不以此准则静默改变。

接入前记录关闭/未接入时的基线，再以相同输入、规模、工具链、features 和构建配置比较开启后的耗时、内存、I/O 及产物体积。远端模型波动不能当作本地采样收益；未测量时不声称低开销或性能改善。本项目仍遵守根 AGENTS.md，不保留或新增自动化测试、夹具与基准程序，不运行 `cargo test`。

## 7. 应用准则时的核对项

- 新增或修改有状态组件时，主动检查是否需要 RuntimeMetric、MemoryMetric 或 Snapshot；不以没有现成监控消费者为理由省略合理的轻量接口。
- 指标类型、字段单位、范围、缺失/估算和恢复语义清楚；读取不会改变业务状态。
- Snapshot 的大小、一致性和复杂度明确，不是未筛选的内部对象深拷贝；普通指标采集不隐含 I/O 或完整扫描。
- Metric/Snapshot 属于观测 contract；模型工具权限、实时事实刷新和任务检查点继续各自管理。
- 性能观测方案优先采用成熟 Agent/采样工具/规范化 SDK，必要业务观测保留明确接口；没有新增零散自定义埋点宏体系。
- 具体平台接入可隔离、资源有界，实际开销与部署影响有证据；未部署时不声称已经具备平台监控能力。

本次仅新增通用准则及引用，尚未新增 Metric/Snapshot 实现或安装、启用任何监控 Agent，也未改变生产代码、依赖、编译配置或进行性能测量。
