[通用开发](README.md) · [文档总索引](../README.md)

状态：已确认。依据：用户明确采用以设计文档为核心的开发方式（2026-09-11）。

## 设计依据

`docs/` 承载项目的技术准则与产品实现方向。当前已确认的设计约束实现；代码反映实际实现状态，两者不一致时应定位原因并消除偏差。

用户最新明确要求优先，并应同步到相应设计文档。`AGENTS.md` 约束开发方式、代码边界与验证要求，领域文档描述目标、行为和验收标准。发现两者冲突时应明确冲突及处理依据，不静默挑选方便实现的版本。

研究材料、备选方案、历史记录和未决问题不能直接作为已确认要求。已有文档不会因本约定生效而自动获得确认；涉及某个领域时先核实其当前有效规则和适用范围。

## 文档应明确什么

按功能复杂度记录足以支持实现与验收的内容，不强制为小改动创建长篇设计：

- 问题与目标：服务谁、使用场景、期望结果。
- 范围与边界：本轮做什么、不做什么，与已有能力如何衔接。
- 行为规则：正常流程、状态变化、异常处理、资源限制及必要的恢复语义。
- 验收标准：用具体场景描述预期结果，包含关键边界和失败情况。
- 未决问题：尚缺少的事实或尚未确定的产品取舍。

通用开发主题直接放在 `common/`，Agent 特有规则放在对应领域目录。一个规则保留明确的维护位置，其他文档通过链接引用，减少重复描述产生的冲突。

## 确认与演进

设计状态与实现状态分别记录：“已确认”表示可以作为实现依据，不表示功能已经完成。设计可标为草案、已确认或已替代；实现可标为未实现、部分实现或已实现，并说明范围。

确认针对本轮范围，无须等待整个产品定稿。用户已经明确的规则直接记录；会影响产品方向、外部行为或兼容性的未决取舍，在相关实现开始前明确。模块内部的常规编码选择由实现者依据现有准则处理。

当前正文始终描述当前有效设计。重要变化记录日期、变化内容、原因和替代关系；需要保留旧方案时明确其历史身份，不与当前规则混写。变更记录可留在所属文档中，不要求每次修改单独创建文件。

## 开发流程

1. 定位相关文档，确认本轮有效设计与验收标准，再检索现有实现和调用关系。
2. 检查规则是否完整、相互一致，是否覆盖关键异常和边界。必要时用小规模原型或实际证据验证假设，并将结论反馈到设计中。
3. 新增功能或改变行为时先更新设计。已获用户明确授权的要求直接落实；关键未决取舍先明确，再实现依赖部分。
4. 按设计实现，复用已有能力并遵循模块边界。发现设计不可行或存在冲突时，将具体原因反馈到文档，不擅自改换产品目标。
5. 按验收标准检查实际行为，执行根 `AGENTS.md` 要求的验证，更新实现状态、已知限制和重要变更记录。

## 问题排查

排查围绕“预期行为、实际行为、差异原因”展开，并保留必要的复现条件与证据。

| 问题来源 | 处理方式 |
| --- | --- |
| 设计缺少规则或规则相互矛盾 | 先修正设计与验收标准，再按修正后的规则实现 |
| 设计明确，实现偏离 | 修复代码，按原验收标准验证；不为迁就错误实现改写设计 |
| 外部协议、依赖或运行环境与假设不符 | 核实实际约束，判断应修复适配还是调整设计，并记录必要的适用条件 |

设计层面的漏洞、重要边界和长期有效的排查结论沉淀到所属文档；一次性的实现笔误无需都转化为产品规则。

文档逻辑完整可以减少歧义，但不能保证代码没有实现错误，也不能证明性能、并发行为或外部服务符合假设。仍须按项目约定完成编译检查和必要人工验证；本流程不改变项目不保留自动化测试、测试夹具和基准程序的要求。
