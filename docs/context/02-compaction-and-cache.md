# 02 · 上下文压缩与缓存命中率的平衡策略

[阅读索引](README.md) · 上一篇：[01 · 原始调研](01-ch-research.md) · 下一篇：[03 · 可配置策略设计](03-context-strategy-design.md)

本文根据用户提供的调查材料整理，并结合当前项目实现说明落地边界。材料中“类似 pi”的描述用于指代策略形态，不作为对 pi 某一版本实现的独立核验；下文数值均为示例或待校准参数，不是性能实测结果。

核心结论：**在 Epoch 内保持前缀稳定、持续追加，在 Epoch 边界通过低频且保真度高的 checkpoint 清理上下文。CH 是优化手段，任务质量、总成本和上下文可用空间才是最终约束。**

后续可配置设计见[上下文策略与压缩配置设计](03-context-strategy-design.md)：进一步区分 `append / selective` 构建策略、轮次 / 水位 / Token 量触发、压缩目标和阈值来源，补充动态选取对前缀稳定与证据保真的取舍。该文为设计提案，新增配置尚未实现。

## 1. 高 CH 不等于上下文占用少

本文的 CH（Cache Hit）默认指 Token 缓存命中率：

```text
CH = 缓存读取 input tokens / 全部 input tokens
```

例如窗口为 200k，实际输入为 193k，其中缓存读取 185k、新输入 8k，CH 约为 95.9%，但输入仍占用 193k。缓存读取已经包含在总输入中，不能重复相加，也不能从窗口占用中扣除。

缓存主要复用重复前缀的计算，可能降低输入费用和首 Token 延迟（TTFT）；它不会删除历史，也不保证长上下文的输出速度等同于短上下文。实际效果取决于模型、推理实现和服务商计费，不能仅凭 CH 推导速度或成本。

Coding Agent 的额外风险是信息过期：旧日志、旧搜索结果、已经修改的源码和旧 diff 持续留在历史里。即使这些内容命中缓存，模型仍需从多个版本中判断当前状态。因此，150k 上下文、98% CH 不一定优于 50k 上下文、80% CH；应比较任务结果和总消耗。

## 2. 两种策略的取舍

| 维度 | 类似 pi 的锯齿策略 | 显式 Context Epoch 策略 |
| --- | --- | --- |
| 基本方式 | 平时只 append，接近窗口预算上限时提前批量 compact | Epoch 内只 append；达到空间或质量触发条件后重建工作上下文 |
| 压缩时机 | 主要由容量高水位驱动 | 容量高水位、阶段完成、大量信息过期等共同驱动 |
| 缓存收益 | 前缀连续稳定，利于复用增长的历史 | Epoch 内稳定；切换时接受部分前缀失效并重新积累缓存 |
| 上下文质量 | 压缩前可能长期携带冗余、冲突版本 | 在边界合并当前状态，清理已失效证据 |
| 压缩产物 | 批量摘要或摘录加近期历史；具体保真度取决于实现 | 明确的任务 checkpoint 加近期完整交互 |
| 主要代价 | 上下文平均占用可能较高，旧信息持续干扰 | checkpoint 有构建成本和信息损失风险，过于频繁会削弱缓存收益 |
| 适用倾向 | 历史仍有用、状态变化少、缓存收益占比较高 | 长时编码任务、文件反复修改、工具输出多、阶段边界清晰 |

二者不是互斥算法。**锯齿是上下文大小随时间变化的形态；Epoch 是对每一段稳定上下文的生命周期建模。** 锯齿式 compact 之后自然进入新一代上下文；显式 Epoch 的价值是补齐切换策略、状态保真和工具证据生命周期，而不只是换一个名称。

```text
Epoch 1：20k → 45k → 80k → 120k → 150k
                                      │ 完整工具批次结束，构建 checkpoint
                                      ↓
Epoch 2：                            55k → 75k → 110k → …
```

这些数值仅演示高低水位。前缀稳定提供缓存命中的机会，不保证命中；缓存驻留时间、路由和服务商策略仍会影响实际 CH。

## 3. 推荐策略：容量兜底，质量触发，边界重建

### Epoch 内保持稳定

将变化慢的 System、工具定义和项目规则放在稳定部分，将本代任务 checkpoint 放在其后，随后追加交互和工具结果。避免每轮重新生成首部任务摘要、重排工具或覆盖历史。

稳定内容也要反映用户最新要求。任务或约束发生变化时及时记录，不应为了缓存继续使用失效规则；需要重建时进入新 Epoch。

### 用高低水位控制容量

设 `W` 为模型上下文窗口，`H` 为压缩高水位，`L` 为压缩后目标，满足 `L < H`。高低水位之间留出足够空间，避免刚压缩完就再次触发。

可以从窗口的 70%～80% 开始评估高水位，但这只是初始候选，不是统一默认值。预算应覆盖完整请求，并预留输出、预计新增工具结果和估算误差：

```text
H ≤ W − 输出预留 − 下一批新增输入预留 − 安全余量
```

各模型对输出、思考及窗口的口径可能不同，应以适配器契约配置。字节限制和 Token 窗口也必须分开：逻辑 JSON 字节只能用于近似诊断或本地边界，不能直接解释成真实 Token 利用率。

不要等服务端报超限才压缩。工具结果需在采集阶段有界输出，大文件采用片段或引用；在下一次模型调用前，基于新增输入重新评估。若保留的必要信息已超过预算，应明确暂停或报告超限，不能静默截掉用户约束。

### 允许质量触发，但避免频繁重建

即使尚未到容量高水位，也可以在阶段结束、任务方向改变，或大量源码和工具结果已过期时考虑切换。判断依据是清理收益是否足以覆盖重建成本，而不是固定“每 N 轮 summarize”。

质量触发可设置最小 Epoch 长度或最小可回收量，防止小幅变化反复触发；容量安全和明确的任务切换不受此限制。阈值应通过同类任务对照校准。

### 在安全边界提交

只在工具批次完整结束、下一模型请求尚未发送的边界 compact。工具调用和对应结果成组保留或归档，不能留下孤立结果；厂商要求的 opaque 续接数据也必须按协议保留或合法结束。

建议先构建并校验候选 checkpoint，再持久化新一代上下文，成功后切换。失败时保留可恢复的旧状态，不清零任务预算或丢失待处理工作。Epoch 是上下文代际，不是新任务，也不等于新建服务端缓存对象。

## 4. Compact 应生成工作 checkpoint

一句自然语言摘要不足以承载编码任务的恢复状态。建议采用以下概念结构；这不是当前已实现的 Rust 类型：

```text
CompactedContext {
    task, constraints
    decisions[], discoveries[]
    filesTouched[], filesRelevant[]
    currentState
    completed[], todo[]
    failedApproaches[]
    importantToolResults[]
    conversationSummary
}
```

保留内容应满足以下要求：

- 用户目标、明确约束和授权边界准确保留；被后续要求替代的内容标明关系。
- 决策记录“选择及原因”，失败方案记录“失败条件及原因”，避免重试已排除的路径。
- 文件与关键符号保留精确名称，当前状态区分已完成、未验证、失败和待执行。
- 验证证据记录命令、结果、对应代码版本或时间；旧版本上的成功不能当作当前版本已通过。
- 重要工具结果保留来源和可恢复引用；摘录、推断和已核实事实明确区分。
- 每类内容和总量都有上限；超限显式报告或转存可检索证据，不无限累积历代摘要。

结构化字段只能降低遗漏风险，不能使压缩无损。应优先直接携带已有结构化状态，再用摘要补充对话背景；若引入模型总结，必须计入额外调用、Token 成本和延迟，并校验关键约束、标识符及证据完整性。

## 5. Tool Result 生命周期与前缀稳定的协调

| 状态 | 活跃上下文中的内容 | 恢复方式 |
| --- | --- | --- |
| HOT | 最近且仍相关的完整工具批次，受输出上限约束 | 直接使用，截断结果保留标记 |
| WARM | 关键片段、diff、结论和来源 | 按来源补读 |
| COLD | toolCallId、路径或产物引用、版本/hash、短摘要 | 从文件或持久化归档恢复 |

**降级旧 Tool Result 会改写前缀，因此不要在 Epoch 内每轮原地执行 HOT → WARM → COLD。** Epoch 内可更新外部元数据、追加“旧版本已失效”的简短标记；实际删减和替换统一放到 Epoch 边界。新工具结果在首次进入上下文前就应限制大小，避免先注入大段日志再频繁清理。

当前工作区文件是当前源码状态的依据，但重新读取只能得到现状，不能还原旧版本。历史失败日志、当时的 diff 或远端响应若仍可能用于决策，应有持久化引用；hash 能校验内容，不能单独恢复内容。只有在来源确实可恢复或证据已不再需要时，才移除完整正文。

## 6. 用任务指标约束 CH 优化

| 指标 | 口径与用途 |
| --- | --- |
| `cache_hit_ratio` | 缓存读取 Token / 总输入 Token；汇总用总量加权，并报告 usage 覆盖率，未知不能当零 |
| `context_utilization` | 单次完整输入 Token / 模型窗口；标明实测或估算，输出余量单列 |
| `context_growth_rate` | 每轮净新增输入量，判断接近高水位的速度 |
| `stable_prefix_tokens` | 稳定前缀规模；不等于实际缓存命中量 |
| `history_tokens`、`tool_output_tokens` | 定位增长来源；工具结果若已含在 history 中，不再重复求和 |
| `compaction_count`、压缩前后大小 | 观察切换频率、回收量和压缩后是否很快再次触顶 |
| `effective_context_ratio` | 当前任务必要信息 / 全部上下文，仅作为人工标注或启发式估计，不能当作精确服务商指标 |
| 任务结果、重读次数、状态遗失 | 检查清理是否引入返工、重复失败或约束遗漏 |
| 总费用、TTFT、输出速度、任务耗时 | 判断缓存与压缩最终是否有收益，包含 compact 和后续补读成本 |

例如必要信息估计为 45k、总上下文为 120k，有效上下文比例约为 37.5%。这个比例能辅助识别冗余，但“是否必要”往往依赖事后判断，应说明估计方法和局限。

比较策略时固定模型、任务、工具输入、初始状态及缓存条件，并覆盖多个 Epoch；不能只挑稳定期 CH，忽略切换后的重新计算和补读。目标是在任务正确性得到保证的前提下，降低整个任务的成本和耗时，而不是单独最大化命中率。

## 7. 当前项目的基础与后续方向

当前已有批量压缩基础，详见 [缓存与输入预算](05-cache-and-input-budget.md)：

- [`Context::compact`](../../agent-core/src/context/compaction.rs) 按逻辑字节高水位或消息数上限触发，低水位作为保留近期历史的目标；保留指令原文，对旧 assistant/tool 内容生成有界原文摘录，按完整工具批次处理，并递增历史代数。
- [`runtime::prompt::prepare`](../../agent-core/src/agent/runtime/prompt/input.rs) 在模型请求准备阶段调用 compact，前后校验工具协议，再补充记忆与运行状态等输入，并检查上下文硬字节上限。
- 现有过程不额外调用模型；`runtime.context.compacted` 记录前后逻辑大小和归档信息。它已经具有锯齿式切换及代际观测基础，但不能据此认为已实现本文提出的结构化 checkpoint、质量触发或 HOT/WARM/COLD 管理。

后续宜复用现有边界：上下文压缩与 checkpoint 数据能力放在 `agent-core::context`，Epoch 触发和执行衔接放在 `agent-core::agent::runtime::prompt`；应用负责配置，具体 vendor 负责缓存协议、续接处理和用量转换。不要为了 Epoch 新建一套 Provider contract，也不要让 vendor 决定任务历史的语义取舍。

优先补强 checkpoint 的状态与证据保真、工具输出引用和完整请求预算，再评估质量触发。保留现有高低水位作为容量兜底，用观测结果决定阈值；缓存协议留在 Provider 层，Context Epoch 的生命周期留在 Runtime 层。

本文仅整理设计与核对当前实现，未修改运行时代码，未测量性能、费用或发布体积，也不将示例中的 CH 和阈值视为收益承诺。
