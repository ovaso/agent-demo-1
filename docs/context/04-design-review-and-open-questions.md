# 04 · 设计完整性与待决问题

[阅读索引](README.md) · 上一篇：[03 · 上下文策略与压缩配置设计](03-context-strategy-design.md) · 实现参考：[05 · 缓存与输入预算](05-cache-and-input-budget.md)

整理日期：2026-09-11。状态：对当前设计框架的评估及后续研讨清单，尚未形成完整的执行规格。

## 1. 当前结论

当前设计已明确“有哪些选择、分别负责什么”，作为策略框架已较完整；尚未明确所有选项“具体如何运行、失败时如何处理”，还不能视为可直接编码与验收的完整详细设计。

本阶段重点是补齐执行流程、数据边界与确定的行为规则，而不是继续增加模式数量。第 03 篇中的配置示意、实现顺序及本篇建议均不等同于已经支持的功能。

## 2. 已形成的设计方向

- 上下文构建使用 `append / selective` 两种具有行为差异的策略。
- 压缩触发独立支持轮次、水位、Token 量；轮次可与一种容量条件按 OR 组合。
- 触发阈值与处理后目标分开；百分比目标指向可用输入预算，不表示保留压缩前内容的比例。
- `manual / auto` 表示阈值来源；`manual` 不等同于用户手动执行压缩。
- 处理方法独立于触发方式。当前有界摘录不能被描述成结构化 checkpoint 或精准上下文选择。
- 硬容量限制、用户有效约束与工具协议完整性适用于所有策略；CH 和精准性收益需要观测验证。

## 3. 六类待补设计

| 议题 | 当前缺口 | 后续应形成的具体结果 |
| --- | --- | --- |
| 请求构建流程 | `selective` 先选取还是先判断容量？压缩后是否再次选择？完整请求何时估算？ | 确定的执行顺序、触发点、预算检查点和持久化边界 |
| selective 选择规则 | 如何判断相关、有效、过期？如何分配预算、排序、去重和补取遗漏？ | 可执行的选择算法、必保留集合、输入输出上限与补取流程 |
| 压缩产物与保真 | 第一版继续摘录还是引入 checkpoint？哪些信息原样保留？历代摘要如何合并？ | 压缩产物结构、保留规则、版本信息和有界合并方式 |
| Token 计量与 auto | 窗口来自哪里？如何估算完整请求？未知模型如何处理？自动阈值何时改变？ | 计量契约、估算来源、未知情况处理、推导规则和生效值展示 |
| 状态与失败处理 | 模式切换如何处理现有状态？失败、无回收效果和必要内容超限时如何处理？ | 可恢复状态、模式迁移规则和逐类确定的失败行为 |
| 配置与验收 | 最终字段、默认值、合法组合和旧配置冲突规则未完全固定 | 配置契约、迁移说明、必要的编译检查和人工验证场景 |

请求构建可以围绕以下候选流程研讨，但其顺序尚未定稿：

```text
读取状态 → 选取上下文 → 估算完整请求 → 判断触发
        → 压缩或更新 checkpoint → 重新组装与校验
        → 持久化 → 发送
```

需要进一步确定是否有循环重建、如何限制尝试次数，以及是否在重组后重新选择。不能把候选流程直接当作实现规格。

## 4. 需要确认的三层数据边界

建议明确以下逻辑分层，具体类型、存储格式和接口尚待设计：

| 层次 | 内容 | 主要作用 |
| --- | --- | --- |
| 完整历史与证据存储 | 可恢复交互、工具结果及来源引用 | 补取、追溯和恢复；未被选中不代表删除 |
| 工作状态与 checkpoint | 当前目标、有效约束、决策、进展和必要证据 | 跨压缩边界延续任务状态 |
| 本次请求视图 | 当前实际发送给模型的消息与工具等输入 | 由构建策略产生，受单次输入预算约束 |

下一步需要逐项说明“压缩”作用于哪一层。缩减本次请求、更新 checkpoint 与删除持久化历史是不同操作；本轮设计没有要求通过压缩自动删除完整历史。

同时需要明确轮次计数、上下文代数与每次请求视图之间的关系：视图变化未必意味着 checkpoint 更新，只有定义清楚的成功提交才重置相应计数。

## 5. 建议的阶段划分

以下是详细设计的收敛建议，供后续研讨，不表示已经批准或实现全部能力。

### 第一阶段：可执行的 append 与手动触发设计

明确 `append`、手动轮次 / 水位 / Token 触发、压缩目标与现有摘录方法的完整行为。比例与 Token 配置依赖完整输入计量，需同时补齐预算口径，不能直接转换现有逻辑字节水位。

本阶段的完成条件包括：有效配置有确定行为；触发和目标口径一致；轮次与上下文状态可恢复；工具批次闭合；压缩失败和超限有明确结果；旧配置迁移无歧义。

### 后续阶段：checkpoint、selective 与 auto

先明确可恢复历史、checkpoint 和请求视图的数据关系，再分别细化选择算法与自动阈值算法。各能力满足自己的行为契约后再开放配置，不以占位选项代替实现。

动态选取可能改善有效信息占比，也可能遗漏上下文或增加补读；评估时需计入选择、重建与后续恢复成本，不仅比较 CH 或输入长度。

## 6. 后续研讨建议顺序

1. 确认第一阶段范围和三层数据边界。
2. 固定一次请求的构建、触发、处理和提交顺序。
3. 定义计量口径、配置契约、默认值及兼容行为。
4. 列出恢复、模式切换、失败和无法回收的确定处理方式。
5. 结合项目验证约定，补充必要编译检查与人工场景；当前不新增自动化测试、夹具或基准程序，也不执行 `cargo test`。
6. 再深入研讨 `selective` 的证据选择和 `auto` 的阈值推导。

本篇记录的是设计完整性讨论，未修改运行时代码，未建立性能、费用或上下文精准性的实测结论。
