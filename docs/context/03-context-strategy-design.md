# 03 · 上下文策略与压缩配置设计

[阅读索引](README.md) · 上一篇：[02 · 平衡策略](02-compaction-and-cache.md) · 下一篇：[04 · 设计完整性与待决问题](04-design-review-and-open-questions.md)

日期：2026-09-11。状态：设计提案，尚未实现本文新增的配置和策略。

本文承接 [CH 调研材料](01-ch-research.md)和[上下文压缩与缓存命中率的平衡策略](02-compaction-and-cache.md)，将 CH、上下文增长与上下文有效性的讨论整理为可组合的配置设计。示例阈值仅用于解释语义，不是推荐默认值或实测结论。

## 1. 设计结论

不采用 `cache / balanced / compact` 三档级别。三档主要是同一种容量压缩算法的不同参数，不能表达动态选取上下文的行为差异，也不能把“更早压缩”解释成“上下文更精准”。

改为分别配置：

| 维度 | 选项或参数 | 负责的问题 |
| --- | --- | --- |
| 上下文构建 | `append` / `selective` | 本次模型请求携带哪些内容 |
| 压缩触发 | 轮次 / 水位 / Token 量，可组合 | 什么时候处理工作上下文 |
| 压缩目标 | 目标 Token 数或可用输入预算比例 | 处理后希望保留多大上下文 |
| 阈值来源 | `manual` / `auto` | 谁确定触发值和目标值 |
| 压缩方法 | 当前有界原文摘录；后续可扩展 checkpoint 等 | 如何保存被压缩内容中的必要信息 |

CH 是观测结果，不设置 `CH_TARGET=95%` 一类运行控制目标。更高缓存命中率、更短上下文和更准确的任务结果之间不存在直接等价关系；应比较整个任务的质量、费用、耗时与返工。

## 2. 上下文构建策略

### append：增长式

当前代上下文持续追加交互，达到触发条件后集中压缩或重建。其优势是历史连续、前缀稳定，提供缓存复用机会；代价是在重建之前持续携带可能过期或无关的信息。

锯齿描述的是“增长—压缩—再增长”的大小曲线。Epoch 描述的是一代工作上下文的生命周期，不是与锯齿互斥的算法，也不专属于某个平衡档位。

### selective：动态选取

每次请求根据当前任务、有效状态和证据，从可恢复的历史与来源中选择需要的内容，构建本次工作上下文。它可以替换、缩减或重排动态上下文，而不是仅在达到水位时裁剪历史。

它有机会减少无关信息和过期版本的干扰，但不能保证模型回复更精确。关键约束漏选、因果背景缺失以及额外检索或模型调用都可能抵消收益；选择成本、补读次数和错误率需要独立验证。

实现原则：

- 区分完整可恢复历史、当前任务状态与本次请求视图；未选中不等于删除。
- 必须携带当前有效的用户目标、约束、授权边界和待处理状态。被新要求替代的旧约束应保留可追溯关系，不能继续当作现行规则。
- 稳定规则和工具定义尽量保持稳定；动态内容尽量采用确定顺序，减少没有语义收益的重排。
- 工具调用与结果按完整批次选取；厂商 opaque 续接数据必须满足协议约束。不能为降低输入量任意拆开依赖链。
- 证据保留来源、版本和可恢复引用。工作区当前文件不能替代所有历史日志、旧 diff 或远端响应。
- 选择器自身输入、输出和成本有界；无法保留必要信息时明确报告，不静默丢弃约束。

两种构建策略均可使用 Epoch 表示 checkpoint 的代际。`selective` 每次选择不同的请求视图，不必每次都生成或持久化一个新 checkpoint。

## 3. 压缩触发与组合

| 触发方式 | 含义 | 示例 |
| --- | --- | --- |
| `turns` | 距上次成功压缩或 checkpoint 重建完成后的轮数 | 每 20 轮 |
| `watermark` | 本次完整请求输入 Token 占可用输入预算的比例 | 达到 75% |
| `tokens` | 本次完整请求输入 Token 的绝对量 | 达到 60,000 Token |

一轮建议定义为一次成功完成的模型响应及其对应工具批次全部处理完成；无工具调用时，在响应完成后计数。失败请求和未完成批次不算已完成轮次。计数属于各 actor 的上下文状态，需随检查点恢复，不能因进程重启或 `/resume` 清零。

水位和 Token 量是同一种容量条件的两种单位。轮次条件可以与一种容量条件同时启用，采用 OR：任一条件满足就在安全边界处理。初版不同时配置百分比高水位和绝对 Token 高水位，避免重复表达同一限制。

`tokens` 不表示任务累计消耗，也不表示自上次压缩新增的 Token。未来若确需按新增量触发，应另定义 `growth_tokens`，不能复用同一字段。

`append` 在触发后批量压缩工作历史；`selective` 每次请求仍独立选取，触发后执行工作上下文压缩或 checkpoint 更新，并重新构建请求视图。若动态选取始终保持低占用，容量条件可能不触发；轮次条件仍可独立触发 checkpoint 更新。上述处理不自动删除完整持久化历史。

只按轮次触发也必须受硬容量限制保护，不能等轮次到达才处理超限请求。阶段完成、任务方向改变和大量证据过期可以作为未来的质量触发条件，待有可靠信号后另行定义，不隐藏在 `auto` 内。

## 4. 水位、目标与单位

设模型窗口为 `W`，可用输入预算为 `B`：

```text
B = W − 输出预留 − 下一批新增输入预留 − 安全余量
H = B × high_ratio
L = B × low_ratio
```

各模型对输出、思考与窗口的口径由适配器明确。当前请求已经包含的工具结果不再作为“下一批新增输入”重复预留。完整输入估算应包括系统规则、工具定义、记忆、历史和协议附加内容，不能只统计 history。

百分比模式要求 `0 < low < high <= 1`；绝对 Token 模式要求 `0 < low < high <= B`。仅轮次触发时仍需指定压缩目标，但可省略容量触发高水位。容量参数中的 `unit` 同时约束高低水位单位。

低水位是压缩后的总输入目标，不是保留原上下文的比例。例如 `low = 0.40` 表示目标为可用输入预算的 40%，不是压缩前内容的 40%。高低水位已表达回收空间，初版不再增加可能与之冲突的“压缩比率”。

工具完整批次、稳定输入和必要约束可能使结果高于低水位，因此低水位是目标，硬上限是约束。无法继续回收时记录原因；若仍超出硬预算则暂停或报错，不能静默截断必要内容，也不能反复空压缩。

当前项目的高低水位使用逻辑 JSON 字节，不能直接标成 Token 或模型窗口利用率。落地比例配置前，需要模型窗口信息、输出预留和 Token 估算能力，并标注计量来源与估算误差；缓存读取 Token 仍占输入空间，不能从容量中扣除。

## 5. manual / auto 与配置示意

`manual` 表示用户指定阈值，达到条件后仍自动处理；用户手动执行压缩是另一个命令能力。`auto` 只负责推导阈值，不擅自改变上下文构建策略、启用其他触发类型或选择另一种压缩方法。

`auto` 的推导算法、上下界和重算时机尚未确定，需结合模型窗口与输入增长数据设计。启用时应展示实际生效阈值和推导依据；基础信息缺失时明确报配置不可用，不能以字节比例冒充 Token 水位。实现前不接受无实际行为的 `auto` 选项。

下面使用 TOML 展示字段关系，**不是当前应用已经支持的配置文件格式**；最终环境变量或配置文件映射在实现时确定。

```toml
[context]
mode = "append"                     # append | selective

[context.compaction]
threshold_mode = "manual"            # manual | auto
every_turns = 20                     # 可选，正整数；省略表示不启用轮次触发

[context.compaction.capacity]
unit = "ratio"                      # ratio | tokens
high = 0.75                         # 可选，省略表示不启用容量触发
low = 0.40                          # 压缩后总输入目标
```

该例表示增长式上下文，每 20 轮或达到 75% 水位时处理，目标降到 40%。改用绝对 Token 配置时，仅替换容量段：

```toml
[context.compaction.capacity]
unit = "tokens"
high = 60000
low = 30000
```

只按水位或 Token 量触发时省略 `every_turns`；只按轮次触发时省略 `high`，仍提供 `unit` 和 `low`。启用压缩时至少选择一种触发条件。关闭压缩应使用明确的独立开关，硬预算检查始终保留。

显式参数优先于推导默认值；`auto` 的参数覆盖规则应在算法落地时明确并统一校验。旧字节水位与新 Token 配置不能互相隐式换算；两套同时显式配置时应报告冲突，迁移前保持旧配置原有语义。

## 6. 处理方法、提交边界与可观测性

触发时机和压缩方法分别负责“何时”与“如何”。当前有界原文摘录不等同于模型总结或结构化 checkpoint；后续方法实现后再暴露选项，不能只加配置名称。

复用完整工具批次结束、下一请求发送前的安全边界。先生成并校验候选上下文，确认协议闭合与预算，再持久化和切换。仅成功提交后重置轮次计数；失败保留旧状态与任务预算。处理无回收效果时记录结果，采用明确的暂停或重试策略，避免每次请求重复进行无效处理。

建议在现有压缩和输入诊断事件上补充以下信息，具体事件字段在实现时确定：

- 构建策略、启用的触发类型、实际触发原因、阈值来源和生效高低水位。
- 本次输入 Token 估算及来源、预留预算、处理前后大小、上下文代数和轮次计数。
- 选取或压缩耗时、补充模型调用及 Token 消耗、目标未达到的原因。
- 缓存命中率与 usage 覆盖率、任务总费用和耗时、证据补读、状态遗漏及返工。

有效上下文比例属于人工标注或启发式评估，不能当作精确服务商指标。对照应固定模型、任务与初始条件，覆盖多个 Epoch，并计入重建、选择与补读成本。

## 7. 当前基础与实施顺序

当前 [`Context::compact`](../../agent-core/src/context/compaction.rs) 支持字节高低水位、消息数限制、有界摘录和完整工具批次处理；[`prompt::prepare`](../../agent-core/src/agent/runtime/prompt/input.rs) 在请求准备阶段执行压缩与协议检查；[应用配置](../../agent-app/src/config/prompt.rs)负责读取现有环境变量。消息数限制不等同于轮次触发，任务累计 Token 预算也不等同于单次请求 Token 高水位。

建议分步落地：

1. 整理独立的策略和触发配置模型，保持现有默认行为与配置兼容；新增选项只随可用能力开放。
2. 明确完整输入 Token 预算与模型窗口来源，支持手动轮次、比例或绝对 Token 触发及目标，补齐持久化计数和诊断。
3. 补强结构化 checkpoint、证据引用和可恢复历史，建立请求视图与持久化历史的分离，再实现 `selective`。
4. 依据实际观测评估 `auto` 和质量触发，避免未校准的自动调整掩盖行为变化。

上下文数据、选取和压缩能力放在 `agent-core::context`；执行衔接、轮次与触发判断放在 `agent-core::agent::runtime::prompt` 及相应状态模块；环境解析和配置装配留在 `agent-app`。vendor 负责协议、续接和用量转换，不决定任务历史的语义取舍。不为模式新增第二套 Provider contract 或独立 crate。

本次仅记录设计并关联既有调研，未修改运行时代码，未测量性能、费用或发布体积。
